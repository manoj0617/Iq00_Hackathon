Yes — the demo needs its own **self-contained workflow context**, separate from the pitch deck. The demo should prove one complete vertical slice, not try to showcase every possible feature.

## Demo Workflow Context

### Demo objective

The live demo should prove this exact product behavior:

> **A user describes the storage outcome they want in natural language. Storage Intelligence converts that request into structured constraints, searches its maintained local storage index, builds an evidence-backed cleanup plan, lets the user review what will change, performs only user-approved Android-supported actions, and then measures the actual result.**

The demo is **not** “look, AI found some files.”

The complete loop is:

**Intent → Understand → Plan → Explain → Review → Act → Re-index → Verify**

---

# Hero demo scenario

Use a student immediately after semester exams.

The student has accumulated:

* Semester 1 PDFs
* lab records
* assignments
* PPTs
* previous papers
* lecture recordings
* downloaded ZIPs
* screenshots
* duplicated PDFs
* multiple accessible copies of media/files received or downloaded through WhatsApp
* Semester 2 material that must not be touched
* personal DCIM/Camera photos that must not be touched

Now the student needs storage for the new semester / a large update / offline lectures.

The demo request:

> **“Free at least 1 GB. Keep my Semester 2 files and DCIM/Camera photos. Start with Semester 1 material and exact duplicates.”**

For the presentation deck we can use “2 GB” as an illustrative user request. For the live demo, **1 GB is more practical and reliable** while demonstrating exactly the same workflow.

# What the audience should understand from the demo

Without explaining too much verbally, they should see:

### Natural language has a real function

It transforms:

> “Free 1 GB but don't touch Semester 2”

into structured constraints.

### AI is not the source of truth

Exact duplicates, byte counts, file metadata and recovery calculations are deterministic.

### The product understands context

“Semester 1” can become a meaningful cleanup scope rather than forcing the user to manually search folders.

### Bulk cleanup is explainable

The user knows:

* why something was selected;
* what will be removed;
* what remains protected;
* how much space the plan should recover.

### The system remembers storage state

The local index updates after actions.

# How to build the planner

Internally, the request becomes roughly:

```text
Target:
  recover >= 1 GB

Protected:
  Documents/College/Sem2
  DCIM/Camera

Priority:
  1. exact_duplicates
  2. semester_1
  3. old_downloads

RequireReview:
  semantic_matches
```

Then the deterministic planner retrieves candidates in priority order until:

```text
candidate_bytes >= requested_bytes
```

It respects protected paths and duplicate-retention rules.

That's enough for the hackathon.
